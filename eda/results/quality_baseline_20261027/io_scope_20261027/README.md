# PAD驱动与转换时间约束诊断

[测量与来源](summary.json)来自bcc483e失败32步数据库的独立内存实验。未保存数据库，原输入SHA复核不变，不作为新一轮34步或后仿结果。

转换时间是信号从低电平变高、或从高变低所花的时间，不是时钟周期。内部数据要求0.3ns、内部时钟0.5ns、外部PAD0.6ns。原脚本把全局0.3ns同时压到了外部端口；其中输入时钟本来就设为0.5ns边沿，约束互相冲突。只给端口补写0.6ns无法覆盖更严格的全局限制。

实测逐引脚分类覆盖261720个叶级信号引脚：248103个内部数据、13611个内部时钟、6个外部PAD；另有6个顶层端口。分类没有使用库限制覆盖选项，库中更严格的要求仍然有效。总转换违规由694降至681，实际内部违规仍为681，没有把内部问题当作外部例外移除。

TDO是芯片向外输出JTAG数据的PAD。原PDDW0204CDG驱动后边沿为2.324/2.163ns，更换为原生PDDW1216CDG后为0.580/0.575ns。两者均60×115µm，7个引脚的几何、方向及四库角逻辑/三态属性一致，原生ECO逻辑等价检查开启且成功。新单元的原生GDS三条供电轨横截面也已核验，不扩大Die外框。

部署文件中，io_plan.json明确各信号使用的单元；07步生成并检查5个输入PAD和1个较强输出PAD；25步为控制引脚连接常量单元，TDO的实际数据输入I继续接核心信号。slew_scope.tcl根据当前物理数据库区分数据、时钟和外部PAD，在优化后、报告前刷新新插入的引脚，写出覆盖计数。32/33步仍要求独立报告的实际与总电气违规均为零。不可用新单元替换或分类计数本身宣称时序已达标。

[后续两轮联合修复测量](joint_margin_trial.json)在200ps Setup优化目标下得到Setup−0.101ns/3条违规、Hold+0.117ns、实际/总转换违规546/547、密度82.996%、默认DRC为0，仍未达标。实验中的时钟数据路径0.3ns规则继续影响外部TDO，未被采用。正式脚本保留完整静态引脚分类，32步联合修复的正Setup目标是额外优化余量；最终非负Setup与100ps Hold门禁不变。该实验数据库没有保存或复用，必须重新运行早期83%预算的新完整实现。

[原生分类与RC读回检查](native_constraints_check.json)核验了实际执行脚本SHA。时钟图未建立时全部内部引脚暂按更严0.3ns处理；后端实际识别13611个时钟引脚，外部违规移除后仍有681个内部转换违规。另发现旧RC温度覆盖未生效、实际默认为25°C；新版使用Innovus原生-T，实际读回25/125/0/−40°C且错误旧温度会被拒绝。该API实验只改变内存，没有保存数据库，不能作为重新实现后的结果。
