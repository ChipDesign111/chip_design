# RTL 周期优化：取指行缓冲（2026-11-04，第 2 轮）

承接 `eda/results/lat_rtl_20261104`（交叉开关 FallThrough，端到端 11,895 → 9,832 拍）。本轮继续只改 RTL、不改测试台，目标是把 CPU 自检段的取指开销压到接近“零取指代价”的下限。

结论：改动叠加后，**CPU 自检段 3,650 → 2,337 拍（−36.0%）**，**端到端 9,832 → 8,536 拍（−13.2%）**；相对本轮起点 11,895 拍累计 **−28.2%**。功能、DMA 重叠计数、NPU 周期数均不变，且已在 SDF 门级后仿 17 个用例上全通过（见 §9）。

> 说明：过程中还试过一版“单拍读省 COMPLETE_READ”的 AXI 旁路，RTL 仿真下能再省 138 拍，但**门级后仿证明它会让读数据晚一拍**（§2），已完整回退。本文所有最终数据都来自回退后的版本。

## 1. 现状测量

`tb_serial.sv`（与后仿同协议）在 FallThrough 版本上实测：装载窗口 6,182 拍（TB 协议下限，见 §5），CPU 自检段 3,650 拍。为判断取指还有多少油水，用 `tb_ideal.sv` 做一个**上限探针**：保留真实 SoC，只把 CPU 的取指口强制成“同拍给 gnt、下一拍给数据、数据直接取自镜像”，并同时把 xbar 的取指从端口压住以免污染仲裁。结果：

```
IDEAL cycles=2107 npu_cycles=1035
```

即取指代价为零时自检段最快 2,107 拍，而实测 3,650 拍 —— 有 1,543 拍可抢。且此时 NPU 本身占用 1,035 拍，CPU 复制/比较的串行工作只有约 1,072 拍，说明这 1,543 拍确实全在取指上。

## 2. 改动一：单拍读省 COMPLETE_READ 拍 —— 已试、已回退

原先做过一版：`rtl/axi/axi_adapter.sv` 的 `WAIT_R_VALID` 收到 `r.last` 后直接在本拍给出 `valid_o/rdata_o` 并回 IDLE，不绕 `COMPLETE_READ`。RTL 行为级仿真下它看起来很好（自检段 3,650 → 2,988 拍），但**门级后仿暴露出它是错的，已完整回退**：

- 本 SoC 的读数据直接来自 SRAM 宏的输出 `Q`。`my_mainmem` 用 `sram_clk = ~clk_i` 驱动宏，`port_req_q` 在 `posedge clk_i` 打拍，所以 **`Q` 要到系统时钟的下降沿（周期中点）才有效**，而不是在 `r` 握手那个上升沿。
- 在 `r.last` 当拍就置 `valid_o`，等于让下游在数据还停留在**上一笔事务**的时候就去取 `rdata_o`。`axi2mem` 是组合式 `r_valid`（与 AR 握手同拍），`dm_sba`/`dm_csrs` 又是纯组合直连，于是这个“早一拍”会原样传到 DM 的 `sbdata`。
- 后仿实测：连续读 `[11111111, 22222222, 33333333, 44444444]` 得到 `[xxxx, 11111111, 22222222, 33333333]` —— 干净地整体滞后一笔事务。这解释了后仿里统计区从 `[1038, 93, 62, 93]` 右移成 `[0xc0dec0de, 1038, 93, 62]`，以及 `gate_zero` 里 CPU 自检末尾那次对 NPU 状态口 `0x70000004` 的 `bne` 拿到旧值而跳进 `fail:`。

回退后（数据通路不变，取指往返仍 3 拍）自检段 **2,337 拍**、端到端 **8,536 拍**，比带旁路的版本多 138 拍（约 1.6%）。这 138 拍是**必须付的正确性代价**，不是可以再抢的性能：读数据在体系结构上就只能到下降沿才有效。

同一处保留的 `COMPLETE_READ` 对 cache-line 读（`type_i=1`）本来就是必需的，未做改动。

## 3. 改动二：取指行缓冲 `rtl/soc/my_ifetch.sv`（新模块）

原来每取一条指令就是一笔独立的单拍 AXI 事务，一个来回 2 拍，且事务之间不能重叠。新模块把取指口换成“行缓冲 + 顺序预取”：

- 一条 **LINE_WORDS 字对齐行**用一笔 INCR burst 取回（层叠在 `axi2mem` 上，它本就能一拍一个 beat 地连续回数据）；
- 行命中时**在请求当拍就给 `gnt_o`**，数据下一拍返回，因此顺序代码可以做到 1 指令/拍无停顿；
- 命中行之后的那一行在后台预取，循环体常驻时不产生额外流量；
- **SLOTS 个行**全相联，按 2 位年龄做 LRU 替换。最初的 2 行版本（只保留“当前”和“下一行”）反而更慢（3,496 拍）：向后跳转回到的正是刚被换出的上一行，每次迭代都要重取。4 行仍略差（3,054），8 行才明显胜出（2,662）——对应 `LINE_WORDS=4, SLOTS=8`。

只读通道；burst 只发给 boot ROM 和 SRAM 两个区间（二者都由 `axi2mem` 服务，支持 INCR），其余地址（尤其 DM 停机区，那里只有一条停机指令）退回单字取指，避免任何从端口收到它服务不了的 burst。

实测（`LINE_WORDS=4, SLOTS=8`）：自检段 **2,988 → 2,663 拍**，端到端 **9,200 → 8,875 拍**；`FPROF cycles=2662 grants=1304 stall=568 fills=159 (miss=77 pf=82)`。

## 4. 改动三：行边填边可用 + 换成 8 字行 4 行

**（a）边填边可用。** 原实现要等 `r.last` 才把整行标成有效，于是任何一个 miss 都要等整条 burst 结束才能开跑；预取“抢在 CPU 前面到达新行”时，CPU 明明已经站在新行上，还要再等大半个 burst。现在每收到一个 beat 就 `svalid<=1; slen<=fill_cnt`，tag 在发起填充时就写好，于是**已到达的字立刻可命中**：miss 落在第 k 个字只需等 k 个 beat，预取赶上时 CPU 几乎零等待。部分填充的行不可能被误命中（写入前逐字收紧 `slen`）。

**（b）8 字行 4 行。** 优化 (a) 之后 miss 变得很便宜，行再长一些就能把 miss 次数直接打下来。把参数从 `4/8` 换成 `8/4`：**同样的数据存储量**（4×8×32 = 8×4×32 = 1,024 个触发器），但 tag 比较从 8 路降到 4 路、每行覆盖 32 B，预取覆盖面翻倍。

实测对比（同一 `tb_fp.sv`，均 PASS）：

| 配置 | 自检段拍数 | 端到端拍数 | fills (miss/pref) | 停顿拍 |
| --- | ---: | ---: | --- | ---: |
| 4 字 × 8 行（改动二） | 2,662 | 8,875 | 159 (77/82) | 568 |
| 4 字 × 8 行 + 边填边可用 | 2,448 | 8,647 | 122 (53/69) | 278 |
| **8 字 × 3 行 + 边填边可用** | 2,217 | 8,416 | 27 (3/24) | 24 |
| **8 字 × 4 行 + 边填边可用** | **2,199** | **8,398** | 25 (2/23) | **10** |
| 8 字 × 8 行 + 边填边可用 | 2,199 | 8,398 | 25 (2/23) | 10 |

> 表中 5 行的绝对拍数都是在“单拍读旁路”仍在时测的（§2，已回退），因此整列偏低约 138 拍；行与行之间的**差值**（各配置的取指收益）仍然有效。回退后最终配置的实测值为 2,337 拍。

采用 **8 字 × 4 行**：与 8×8 完全同速，但行存储只有一半（1,024 个数据触发器，和改动二的 4×8 相同），并且命中通路只有 4 路 tag 比较 + 4:1 槽选择，对 20 ns 时序最友好。

改动后全程只剩 **2 次 miss、10 拍停顿**（取指路径的计数，与数据通路的旁路无关），自检段 2,337 拍，距上限探针的 2,107 拍只差 230 拍（占端到端 2.7%）。

```
INT8_SOC PASS cycles=2337  DMA_read_MAC_overlap=62  DMA_write_MAC_overlap=93
```


## 5. 为什么装载窗口（6,182 拍）无法再压

用 `tb_ld.sv` 逐拍打点，一笔 SBA 写的实际时间线是：

```
T=310000 drive                      ← 测试台在下降沿驱动
T=315000   gnt / dm aw_valid / sram aw_valid / axi2sram mem req we=1
T=320000   rvalid（xbar 在 315 边沿寄存 b，320 下降沿被驱动看到）
```

即从驱动到写响应只有 **1 拍**，已经压到物理下限（SRAM 在下一拍的下降沿真正写入）。串行装载每字 3 拍的来源是**测试台自身协议**：驱动→判 gnt→撤 req→判 r_valid→回到任务末尾，共 3 个下降沿，与 RTL 快慢无关。因此不改测试台就无法再省这 6,182 拍（另见 `eda/results/lat_stream_20261104` 的流水装载实验，那是测试台侧才是 2 拍/字的原因）。

## 6. 试过但无效 / 未采纳

| 实验 | 结果 | 处理 |
| --- | --- | --- |
| 行缓冲 2 行（只留当前+下一行） | 3,496 拍，比不缓冲更慢：回跳落在刚换出的行上，每轮迭代都重填 | 弃用 |
| 行缓冲 4 行（4 字） | 3,054 拍，仍慢于 8 行 | 弃用 |
| `cv32e40p_prefetch_buffer` `FIFO_DEPTH` 2 → 4 | 2,996 拍 vs 2,988 拍，无收益 | 弃用 |
| 读通路做成“每拍一笔事务”的全流水 | `axi_xbar` 配置为 `MaxSlvTrans=1`，adapter/axi2mem 都是单事务 | 不可行，改用 burst |
| 加宽 NPU 权重复用/合并 DMA 传输（2 bank → 4 bank） | 会改变 `loads`/`fc1_cycles` 等被固件自检（0x28/0x2c/0x30 必须等于 64）的计数 | 不做 |
| 缩短 DM 装载响应路径 | 已在下限（见 §5） | 不做 |

| 版本 | 自检段拍数 | 端到端拍数 | 相对起点 |

| 本轮起点（FallThrough 之前的基线） | 3,659 | 11,895 | — |

† 该行数据是在“单拍读旁路”仍在时测的（该旁路后来因后仿失败被回退，见 §2），比当前版本少 138 拍。相对趋势不变：行缓冲 + 边填边可用仍然是全部收益的来源，旁路只占其中 1.6%。

装载窗口始终 6,182 拍（TB 协议下限），DMA 读/写与 MAC 重叠始终 62/93，NPU 1,035 拍未变 —— 省下的全是真取指开销。

距理想取指探针的下限 2,107 拍，当前 2,337 拍只剩 230 拍（占端到端 2.7%），且全部落在**每次 load 的 3 拍往返**上（受 §5 的存储时序约束，无法在 RTL 侧消除）。

- 表里的 3.7956 mm² 是**整片 die 的边框面积**，由 floorplan 定死。上一版（`20261104_164956`）也是 3.7956390976 mm²，小数点后十位完全一样 —— 不变的是这个框，不是单元面积。
