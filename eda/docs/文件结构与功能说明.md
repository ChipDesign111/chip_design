# EDA文件结构与功能说明

学习入口是[操作指南](操作指南.md)：从上传部署包开始，顺序完成实现和回传。跑完后用[报告查找与分析](报告查找与分析.md)定位原文、解释字段并填写结论；单个后端步骤查[讲义34步与文件对照](讲义34步与文件对照.md)。只需上传由package_server.py生成的部署包；不用把整个仓库、所有模型或这份文档搬到服务器。

```text
eda/
├── README.md                  入口与流程图
├── package_server.py          本机生成部署包
├── server/                    部署专用程序
│   ├── README.md              部署文件说明
│   ├── bin/eda.sh             加载EDA环境并选择解释器
│   ├── bin/review.sh          轻量结果回传入口
│   ├── bin/flow.py            准备、综合、后端、恢复、报告、交付入口
│   ├── config/                当前SoC的参数与34步教学说明
│   ├── tcl/driver.tcl         有条件执行与检查点控制
│   ├── tcl/steps/             对应讲义的原始操作片段
│   ├── tools/                 几何生成、报告和网表/GDS核对
│   └── template/              保留来源头的课程启动与库配置基础
├── docs/
│   ├── 操作指南.md            从本机打包、部署到服务器运行和回传的主路线
│   ├── 报告查找与分析.md      报告路径、字段、真实路径示例与结论模板
│   ├── 讲义34步与文件对照.md 每个后端动作的文件、作用、原因、效果
│   ├── 基础知识.md            连贯讲解电路与物理实现概念
│   ├── 实施与适配说明.md      修改设计时哪些要改、哪些可以复用
│   └── 文件结构与功能说明.md  本说明
├── tests/                     不消耗商业许可证的开发回归
├── validation/                实际做过的验证范围和证据摘要
└── dist/                      生成的部署包与SHA；不提交Git
```

**哪些配置会生效。**

| 文件 | 含义与使用时机 |
| --- | --- |
| server/config/design.json | 仅作为prepare的默认输入；包含周期、库/宏源路径、CPU数、目标密度、宏坐标和修复上限 |
| server/config/io_plan.json | 六信号PAD映射和每边七个供电/POC位置；需要改布局时先修改并重新打包 |
| server/config/steps.json | 每一步做什么、为什么、预期效果和参数，生成运行报告时读取 |
| 工作目录config/design.json | 准备时固定下来的本轮配置；开始运行后不再随部署目录变化 |
| 工作目录evidence/input_manifest.json | 实际源码、配置、模板与控制程序的SHA；不应手工编辑 |
| 工作目录evidence/doctor.json | 解析出的15份库/工艺资料的身份；重新doctor不能放行库变化后的旧检查点 |
| 工作目录evidence/floorplan_plan.json | 新面积驱动的核心规划结果，不是已经完成的物理布局 |
| 工作目录evidence/geometry.json | floorPlan后读取的实际Die和派生PAD/端口坐标 |

**控制和检查程序。**

| 文件 | 功能 |
| --- | --- |
| server/bin/flow.py | 固定输入、运行工具、锁与中断处理、库身份检查、阶段恢复、自动报告和打包 |
| server/tools/light_delivery.py | 核对完整交付清单后生成轻量复核包；压缩层次网表，大型物理/寄生视图留远端并记录SHA |
| server/tools/generate.py | 按实际宽/高生成外围和端口，适配宏位置；不生成NPU功能RTL |
| server/tools/checks.py | 解析面积、Setup/Hold/DRV、放置、PG/DRC/天线及交付结构；缺失/不认识的报告不能当0违规 |
| server/tools/audit_io_topology.py | 比较插PAD前后所有原信号端点，检查外侧网络只接对应PAD |
| server/tools/audit_io_ties.py | 检查PAD控制脚的Tie值及四个供电网络独立 |
| server/tools/gds_audit.py | 读取GDS记录、引用、单位和选定M4几何；不是独立LVS程序 |
| server/tools/audit_native_io_rails.py | 核对当前库直线IO和Corner的原生长轨；与实际外围连续性共同使用 |
| server/tcl/fanout.tcl | 第32步按当前报告对普通单驱动网络分流，保留天线二极管，检查端点并重新布线/分析 |
| server/tcl/driver.tcl | 在新的Innovus进程中导入/恢复，逐步执行、审计后推进进度，保留实际Tcl片段 |

**模板与执行片段。** template/config提供兼容课程变量的库与SDC基础，template/syn提供Genus初始化/综合，template/pnr提供Innovus初始化。prepare按当前分支替换源码路径、宏选择和工程参数，不会拷贝PDK进仓库。

tcl/steps以01到34对应讲义。23拆成Tap/Decap，29/31/32包含检查及条件修复，34拆成多种导出。它们是生成基础，不能直接在自己的活跃数据库里随意source。生成后的待执行片段在pnr/generated/；实际用过的正文在evidence/commands/步骤号/。

tests/remote_compatibility.py只在独立空闲准备工程上检查兼容性和输入保护；tests/adopt_synthesis_fixture.py是开发验证助手，只能在新工程里复用已经完成且源文件、规范化综合设置和库身份均匹配的综合结果，记录引用来源，不冒称新综合。tests/adopt_physical_fixture.py仅供开发者把已通过的第31步检查点导入新控制程序工程，逐文件核对种子数据库，并保留来源步骤的原输入身份；本工程重新执行32及以后步骤，原生IO几何另做新复核。普通复现实验按操作指南从头综合，不需运行这些助手。

**运行产物。** syn/my_soc_top保存新综合网表与报告；pnr/my_soc_top保存阶段报告、恢复点和最终导出；evidence保存源身份、step_XX.json、逐步运行报告、实际命令、截图和按阶段归档的原始报告。大型数据库、厂商模型和PDK留远端，delivery_manifest.json说明最终回传包与保留位置。

每次prepare都创建新工作目录并保留控制程序快照；以后从部署目录调用入口时会切换到该快照执行。这样更新Git分支不会悄悄改变已经运行到一半的工程。
