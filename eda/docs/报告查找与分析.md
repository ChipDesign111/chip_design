# 跑完以后：报告在哪里、怎么看、能得出什么结论

先按[操作指南](操作指南.md)完成部署与运行。本篇从“终端命令结束了，接下来打开什么”开始。以下命令在服务器 Bash 执行，沿用主指南的 `EDA_DEPLOY`、`EDA_WORK`；所有相对结果路径以 `$EDA_WORK/` 为根。`less` 按 `q` 退出，压缩文本用 `gzip -cd 文件 | less` 查看，不必解压占空间。

## 1．先找到自己的这一轮，判断是否真的完成

重新登录后：

```bash
source "$HOME/Desktop/fullstack_chipdesign/run_env.sh"
cd "$EDA_DEPLOY"
bash server/bin/eda.sh status --work "$EDA_WORK"
```

`Last completed step: 34` 说明进度到了导出，但还要检查工具错误和最终证据。任务仍在运行时先等它结束，不同时调用 report/package。

```bash
if [ -f "$EDA_WORK/evidence/unexpected_tool_errors.json" ]; then
    cat "$EDA_WORK/evidence/unexpected_tool_errors.json"
fi
bash server/bin/eda.sh report --work "$EDA_WORK"
less "$EDA_WORK/evidence/运行报告.md"
```

有未解决错误文件时不能宣布通过。`report` 只是把已有证据组织成文档，不会重新跑物理实现，也不会替未完成步骤补 PASS。

**先辨认三层资料：**

| 资料 | 回答什么 | 用法 |
| --- | --- | --- |
| `evidence/运行报告.md` | 每一步做什么，实际执行了什么，哪些完成 | 先通读建立顺序，记录需要深入看的阶段 |
| `evidence/step_NN.json` | 这一阶段自动检查了哪些项目，引用什么原始报告 | 看 `automatic_checks`，不要把 `commands_completed` 当所有项目都通过 |
| `.rpt`、`.summary.gz`、`.tarpt.gz` 和工具 `.log` | 工具实际写出了什么，具体违规在哪里 | 用来解释结果、定位问题，不能只摘自动摘要 |

`.summary.gz` 是压缩后的时间汇总；`.tarpt.gz` 是压缩后的详细路径文本，不是 tar 压缩包。JSON 是机器可读的结构化记录，字段后面的值就是程序提取的结果。

## 2．确认来源：这个报告对应哪份代码和哪些条件

```bash
cat "$EDA_WORK/evidence/source.json"
cat "$EDA_WORK/evidence/preparation.json"
cat "$EDA_WORK/config/design.json"
cat "$EDA_WORK/evidence/doctor.json"
```

| 文件/字段 | 应理解为 |
| --- | --- |
| `source.json` 的 `git_commit`、`working_tree_dirty` | 部署包来自哪个提交，打包时工作副本有无未提交内容；有未提交内容时结合逐文件 SHA 确认 |
| `input_manifest.json` | 本轮固定的源码、配置及正式程序SHA，保护检查点不被错配 |
| `preparation.json` 的 `rtl_files`、`macro_source` | 综合输入规模和主 SRAM 来源 |
| `functional_retested_here: false` | 本次EDA不执行功能仿真；功能验证须另按仓库流程完成 |
| `config/design.json` | 系统周期、核心规划、宏坐标、修复策略和分析 profile |
| `doctor.json` 的 `libraries_sha256` | 运行时实际用到哪些库文件，内容是否一致 |

本 profile 为单 TT：典型工艺条件下的一个分析场景；IO、标准单元和主 SRAM 时间模型共同参与后端分析。SI 关闭表示没有完整分析串扰影响；原生 low RC 是本环境可用的寄生模型，不能写成高精度签核提取。

还要读 `config/constraints_my_soc_top.sdc` 以及 `config/user_define.tcl`。系统时钟 `sys_clk` 默认 20 ns，JTAG 时钟另有周期，复位与异步路径也有例外。**时序通过只对实际约束、实际被分析的路径成立。** 核对时钟和例外是否符合设计意图，不能为消除红字随意加 false path（免于普通时间检查的路径例外）。

历史结果的综合、01–31和32–34来自分段执行，来源见[结果说明](../results/README.md)。当前正式入口从本轮RTL运行，也支持同一工程正常断点续跑；不同工程的开发检查点导入工具不随分支提交。

## 3．综合报告：先确认做出来的是完整设计

**为什么先看这里：** 一个被误裁成空壳的设计也可能时序很好。先确认 CPU、主存、NPU、DMA 真正进入实现，再比较性能和面积。

```bash
cat "$EDA_WORK/evidence/synthesis.json"
less "$EDA_WORK/syn/my_soc_top/reports/runtime/check_elab.rpt"
less "$EDA_WORK/syn/my_soc_top/reports/runtime/check_map.rpt"
less "$EDA_WORK/syn/my_soc_top/reports/runtime/check_opt.rpt"
less "$EDA_WORK/syn/my_soc_top/reports/area/area.rpt"
```

### 3.1 结构与面积

| 字段或报告 | 含义、判读方法 |
| --- | --- |
| `native_main_srams` | 预期一个 RA1SHD 主 SRAM，避免没选真宏或重复主存 |
| `all_leaf_types_have_library_models` | 映射后每种末级单元都有库模型，避免残留无法实现的黑盒 |
| `npu_dma_area_hierarchy_present` | 预期 NPU/DMA 层次仍存在；还需读原面积报告确认规模合理 |
| `latch_area_um2` | 预期非预期数据锁存器面积为 0；门控时钟单元要结合门控报告区分 |
| Cell Count/Cell Area | 实际单元数量/面积；面积单位 μm² |
| Net Area | 综合阶段的互连估计，不是已布线金属面积，不用于替代单元面积做核心估算 |
| 层次缩进 | 父层包含子层，不能把父与子行再次相加当全芯片面积 |

已有参考综合结果：165606 个映射末级实例，Cell Area 为 4672791.309 μm²。只是用于理解规模；自己的结果以本轮报告为准。

然后看规划和实际几何：

```bash
cat "$EDA_WORK/evidence/floorplan_plan.json"
cat "$EDA_WORK/evidence/geometry.json"
```

前者是估算核心大小，后者是工具对齐合法网格后的实际尺寸。裸片还包含外围、电源空间和布线留白，不能用 Cell Area 直接当裸片面积。最终时间汇总中的 `100% with Fillers` 表示空位被填充单元占满，不表示全部都是逻辑、也不表示布线拥塞 100%。

### 3.2 综合时间、门控与功耗

```bash
less "$EDA_WORK/syn/my_soc_top/reports/others/qor.rpt"
less "$EDA_WORK/syn/my_soc_top/reports/timing/func_tt_1p80v_25c_timing.rpt"
less "$EDA_WORK/syn/my_soc_top/reports/others/clock_gating.rpt"
less "$EDA_WORK/syn/my_soc_top/reports/power/func_tt_1p80v_25c_power_hier.rpt"
```

QoR 是综合质量汇总，包含时钟、关键路径、面积等。路径报告有 Startpoint/Endpoint，即数据出发和被接收的位置，以及 Required Time、Arrival、Slack。

**先看单位。** 当前参考 Genus 关键路径显示 `MET (356 ps)`，356 ps 约为 0.356 ns；QoR 中的系统周期 20000 ps 就是 20 ns。不要把综合报告的 ps 数字直接与 Innovus 标明 ns 的摘要比较。

门控报告说明综合自动插入或识别的时钟门控情况。门控是在无需更新时停止部分寄存器时钟，ICG 是实现这种控制的专用单元。当前 RTL 的 CPU 时钟包装仍为直通，Genus 自动门控已启用；看到 ICG 不代表你已修改 CPU 包装的门控逻辑。

功耗报告单位由报告头确认，脚本使用 μW。动态功耗受翻转活动影响，漏电与器件状态和库条件有关。本轮未加载实际软件负载的 VCD/SAIF 活动文件，属于 vectorless 估计；VCD/SAIF 是仿真记录的信号变化/活动信息。这里可比较估计层次占比，不能写成真实推理任务功耗或芯片实测功耗。

## 4．最终时间：先看填充后的汇总，再追关键路径

### 4.1 找对阶段，避免拿中间结果当结论

| --- | --- | --- |

| `pnr/my_soc_top/reports/postCTS/`、同级 `postCTS_holdFix_check/` | 时钟树后、阶段修复后 | 阶段诊断 |
| `pnr/my_soc_top/reports/postRoute_holdAuto_check/` | 第 32 步布线后修复 | 必须过，但后面还有填充 |
| `pnr/my_soc_top/reports/postFiller/` | 第 33 步最终填充后 | 作为最终状态时序结论 |

**先读 JSON，再核对原文：**

```bash
cat "$EDA_WORK/evidence/step_33.json"
gzip -cd "$EDA_WORK/pnr/my_soc_top/reports/postFiller/my_soc_top_postRoute.summary.gz" | less
gzip -cd "$EDA_WORK/pnr/my_soc_top/reports/postFiller/my_soc_top_postRoute_hold.summary.gz" | less
```

这两个文件名中虽含 `postRoute`，但所在目录为 `postFiller`，因此对应最终填充后分析；报告头的 Command、时间与 JSON 引用也应一致。

### 4.2 Setup/Hold 的字段与验收

Setup：数据要在接收时钟采样前提前稳定，检查“是否太慢”。Hold：数据在采样后仍需保持一小段时间，检查“是否过早改变”。

| 字段 | 含义 | 最终要求 |
| --- | --- | --- |
| WNS (ns) | 最紧张路径的 slack，slack 是时间余量 | Setup/Hold 都 ≥ 0 |
| TNS (ns) | 负余量的累计，说明失败的总体程度 | 两者都为 0 |
| Violating Paths | 报告统计的违规路径数 | 两者都为 0 |
| All Paths | 该次工具分析统计的路径，不是全部 RTL 功能组合 | 辅助确认范围，不拿它作覆盖率证明 |
| `all` | 各路径组总体结果 | 先看这里，再看具体组 |
| `reg2reg` | 寄存器到寄存器路径 | 判断数据运算路径 |
| `reg2cgate` | 到时钟门控控制的路径 | 门控控制也有时间要求 |
| `func_tt_io` | 当前包含 IO 的分析视图 | 确认分析场景正确 |

参考最终摘要为 Setup WNS `+0.710 ns`，Hold WNS `+0.015 ns`，TNS 与违规路径均为 0。这说明该条件下最紧张的 Setup 路径余量为 710 ps，最紧张的 Hold 路径余量为 15 ps。

`hold_target_ns=0.02` 是优化器争取的余量目标，不是另加的 SDC 约束；最终自动验收是 WNS ≥ 0，因此 +0.015 通过现有门槛。余量很小仍应如实保留，不能据此宣布其他工艺角也通过。不要仅用 `20 ns - WNS` 推算“最高频率”，还存在时钟延时、抖动、例外和其他场景。

### 4.3 电气 DRV：时间通过以后仍要看

Setup 摘要下方的 DRVs 表列出：

| 项目 | 专业词的实际意思 | 为什么要修 |
| --- | --- | --- |
| max_cap | 驱动端所带总负载电容超过限制 | 太重的负载影响单元延时与波形 |
| max_tran | 0/1 电平切换所需时间超过限制 | 边沿过慢不符合库的电气要求 |
| max_fanout | 一个驱动所带的负载数量/库定义负载超过限制 | 驱动分配不合理 |
| max_length | 导线长度限制 | 若报告该项，也需要满足 |

查看 Real 和 Total 两组计数，最终都应为 0。当前版本的 Hold 摘要通常不打印这张表，JSON 中 `electrical_drv_table_reported_here: false` 表示未在该报告提供，不是重新测到了零。

若扇出仍有违规，先看当前 `.fanout.gz`，再看 `evidence/fanout_plans/` 与 `evidence/commands/32/`。脚本从实际负载生成分流方案，保留天线二极管，插缓冲后重新合法化、布线与分析。修复中途报告里的红字不等于最终失败，关键是最后独立检查是否清零；解析不完整或不支持的网络会停止。

### 4.4 从一个真实路径看懂时间差在哪里

```bash
gzip -cd "$EDA_WORK/pnr/my_soc_top/reports/postFiller/my_soc_top_postRoute_all.tarpt.gz" | less
gzip -cd "$EDA_WORK/pnr/my_soc_top/reports/postFiller/my_soc_top_postRoute_all_hold.tarpt.gz" | less
```

先看头部的 Beginpoint/Endpoint、Analysis View 和 Path Groups，再读 Required/Arrival/Slack，最后按路径表逐级追踪。

参考最终 Setup 第一条路径从 NPU 的 `core/mult_reg[1]/Q` 到 `core/hb_reg[1][16]/D`，完整层次均在 `i_npu_subsystem/i_npu_core/` 下。原文给出：

```text
Required Time  21.427 ns
Arrival Time   20.717 ns
Slack Time      0.710 ns
```

Setup 的余量是 `21.427 - 20.717 = 0.710 ns`。Required 已包含接收时钟到达、周期、建立时间和 uncertainty 等调整；Arrival 包含发射时钟和数据传播。看到到达时间超过 20 ns 不应直接判失败，因为这不是只测一段组合逻辑的绝对耗时。

路径表中 Cell 是经过的具体器件，Delay 是本段延时，Arrival 是累计到达时间。看延时主要集中在长串逻辑、重负载还是互连，再决定是否需要 RTL 流水、缩短组合链、调整放置或加缓冲。Hold 报告关注最早到达及保持边界，余量方向与 Setup 不同，按其报告等式读，不套 Setup 的减法顺序。

```bash
less "$EDA_WORK/pnr/my_soc_top/my_soc_top_postFiller_drc.rpt"
```

供电的中途 `pg_noDangling.rpt` 排除了悬线检查，不能拿它当第 33 步完整 PG 验收。PG 就是电源与地网络，连接检查回答“是否接通”，不回答大电流时电压降是否足够小。

信号报告可能列出 `VDDPST/VSSPST` 两项 no routing。它们涉及 IO 库抽象未完整表达原生供电轨。本程序只在第 22 步原生 GDS 轨道、角部、四边实际连续布局及四网拓扑证据匹配时分类，并记录在 `step_33.json` 的 `classified_io_abstract_nets`。缺证据或出现其他问题就停止。**正确结论是“未解决信号问题为 0，两项 IO 抽象限制经证据分类”，不能写“原始连接报告零问题”。** 这仍不是独立全芯片 LVS。

Bond 与 IO 的预期覆盖也会在放置检查中单独记录，因为大金属焊盘本就要覆盖对应 IO；不能泛化为任意 overlap 都可忽略。截图 `evidence/34_final_layout.gif` 可帮助理解外围、宏和网格，截图缺失或看起来整齐都不能替代上述检查。

**防止读到被覆盖的中间报告：** `step_NN.json` 中每项通常包含 `report`、`archived_report`、`report_sha256`。前者是服务器原路径，后者是该阶段归档的相对路径。看历史阶段时用 `evidence/stage_reports/NN/` 的归档。下载后原绝对路径仍指向服务器，改按归档相对路径在本地打开，不去手改证据。

## 7．回传后在本机读，保留可追溯关系

按主指南生成 package/review 并下载。解压出的 `core/` 保持服务器相对目录：

```text
core/
├── config/                               本轮参数、SDC、库路径
├── flow/                                 本轮控制程序快照
├── src/chip_design/rtl/、src/filelist_syn.f 本轮源码与清单
├── syn/my_soc_top/reports/                综合报告
├── pnr/my_soc_top/reports/                各阶段时间报告
├── pnr/my_soc_top/*.rpt                   小型物理检查原文
├── pnr/my_soc_top/outputs/manual_final/   小型视图及 gzip 层次网表
├── evidence/运行报告.md                  按阶段的实际记录
├── evidence/step_*.json                   自动验收、原文路径与 SHA
├── evidence/commands/、stage_reports/     实际命令及阶段归档
├── review_manifest.json                  轻量包清单、远端大文件位置
└── delivery_manifest.json                核心交付清单与超限留远端项
```

轻量收集对小文件有大小限制，以本轮 `review_manifest.json` 为准；某大日志没有进入包时，回服务器按原位置读。层次网表在轻量包中另作 gzip 压缩，清单同时保存原文 SHA 和压缩文件 SHA；两者不同是正常的。

`review_manifest.json` 的 `remote_work` 告诉你远端工程根目录，`large_final_views_retained_remote` 列出大视图路径/大小/SHA。完整数据库、PDK 和授权宏继续保留远端。写实验结论时引用相对路径和关键字段，便于别人打开同一份证据复核。
