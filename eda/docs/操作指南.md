# 从现有仓库部署到服务器，跑完 EDA 并分析结果

这份指南从上传现有仓库开始，带你在 `chipdesign` 上完成 `xzx/rtl` 分支的完整 `my_soc_top`：Genus 综合 → Innovus 01–34 步 → 最终检查 → 查报告 → 分析与回传。CPU、总线、主存、NPU、DMA 都在实现范围内。

按正文顺序操作即可。代码块会注明在 **Windows PowerShell** 还是 **服务器 Bash** 运行；工具内部 Tcl 由脚本执行，不需要你另开工具输入。首次采用第 6 节的分段路线；连续运行用第 7 节的 `all`，两条路线选一条。

需要查每个后端动作时看[讲义 34 步与文件对照](讲义34步与文件对照.md)；报告原文、字段和分析方法看[报告查找与分析](报告查找与分析.md)；术语看[基础知识](基础知识.md)。正文说明“应该生成什么”，已有[参考运行报告](../results/run_01_to_34.md)记录“之前实际生成了什么”，不要把两者混用。

## 1．在 Windows 将现有仓库打成部署包

**Windows PowerShell，当前分支的仓库根目录。** 本机独立工作副本是：

```powershell
Set-Location 'C:\Users\zixiang\OneDrive\Desktop\advanced_chip_study\tmp\npu-stream-rtl'
git branch --show-current
git status --short
```

分支应显示 `xzx/rtl`，目录下应有 `rtl/` 和 `eda/`。以后把仓库放在别处时，只改 `Set-Location`。另一份工作目录有未提交代码时，继续用这份独立副本。

直接生成服务器部署包：

```powershell
python eda/package_server.py
```

**做什么、为什么：** 仓库还有训练、仿真和历史实验内容，服务器物理实现不需要全部上传。打包程序选出当前 RTL 和 EDA 程序，保存版本及每个文件的 SHA-256。SHA-256 是文件内容的校验值，用来发现传输损坏或输入变化。

| 文件 | 本步作用 |
| --- | --- |
| `rtl/`、`rtl/filelist.f` | 硬件源码及综合文件清单，决定读取哪些模块和头文件目录 |
| `eda/package_server.py` | 收集正式部署程序和RTL，生成压缩包及来源清单 |
| `eda/dist/chip_design_eda.tar.gz` | 要上传的部署包 |
| `eda/dist/chip_design_eda.tar.gz.sha256` | 整个压缩包的传输校验值 |

**完成标志：** 打包输出 `archive`、`bytes`、`sha256` 和文件数，出现上述两个输出文件。打包只收集当前源码，不执行功能仿真；如修改了功能，应先按仓库功能验证流程验证。

## 2．上传、登录、解压

**Windows PowerShell，仓库根目录：**

```powershell
ssh -o ClearAllForwardings=yes chipdesign 'mkdir -p "$HOME/Desktop/fullstack_chipdesign/incoming"'
scp -o ClearAllForwardings=yes .\eda\dist\chip_design_eda.tar.gz .\eda\dist\chip_design_eda.tar.gz.sha256 chipdesign:~/Desktop/fullstack_chipdesign/incoming/

```

`scp` 复制文件，`ssh` 打开服务器终端；`chipdesign` 使用你已有的 SSH 配置。`ClearAllForwardings=yes` 只对本次连接关闭端口转发，避免转发端口冲突。

**登录后，服务器 Bash：**

```bash
cd "$HOME/Desktop/fullstack_chipdesign/incoming"
sha256sum -c chip_design_eda.tar.gz.sha256
mkdir -p ../deploy
tar -xzf chip_design_eda.tar.gz -C ../deploy
cd ..
bash deploy/server/bin/workspace.sh
source ./run_env.sh
cd "$EDA_DEPLOY"
ls
```

校验应显示 `chip_design_eda.tar.gz: OK`，否则重新上传。`tar`解压到桌面工作区的deploy；workspace.sh生成README.html、路径配置和完整流程入口。双击服务器Desktop/fullstack_chipdesign/README.html可在GUI查看。`ls`应看到：

```text
部署目录 EDA_DEPLOY/
├── server/                    EDA 程序、配置和工具脚本
├── rtl/                       与程序同次打包的硬件源码
├── docs/                      操作与报告分析文档
└── source.json                分支、提交、逐文件 SHA，说明包来自哪里
```

本机路径是 `eda/server/`，解压后是 `server/`，所以服务器入口写成 `bash server/bin/eda.sh ...`。单独上传 `server/` 不够，会缺 RTL 和来源清单。

工作区顶层结构与GUI入口见[服务器桌面工作区](服务器桌面工作区.md)。后续部署、配置、日志和运行结果统一放在这个目录中。

## 3．确认服务器的工艺库和 SRAM 资料

部署包不含 PDK 和授权 SRAM。**PDK 工艺资料**提供本工艺可用的器件、引脚、金属层和规则；**SRAM 硬宏**是内部版图已经确定的存储器，功能 Verilog 模型不能代替其延时、外形和实际几何视图。

课程资料在 `/lec/lab4`，PDK 在 `/lec/pdk/tsmc180`。正式默认配置使用共享PDK路径；下一节建立本轮配置副本，明确选择实际可读的资料，不要求写入其他用户主目录。

**服务器 Bash，部署目录：**

```bash
export EDA_PDK_SOURCE=/lec/pdk/tsmc180
export EDA_MACRO_SOURCE=/lec/lab4/soc_cv32e40p_template_pnr-stu/src/macro/RA1SHD_2048x32M8
ls -ld "$EDA_PDK_SOURCE" "$EDA_MACRO_SOURCE"
ls "$EDA_MACRO_SOURCE"
```

宏目录应有以下三个文件，并有 `.gds` 或 `.gds.gz`：

| 文件 | 为什么需要 |
| --- | --- |
| `RA1SHD_2048x32M8_tt_1p8_25C_syn.lib` | SRAM 引脚、逻辑和延时模型，供综合和时序分析 |
| `RA1SHD_2048x32M8.vclef` | 外形、引脚位置等物理抽象，供布局布线 |
| `RA1SHD_2048x32M8_ant.lef` | 天线规则相关补充信息 |
| 宏 GDS | 存储器实际几何，供最终合并 GDS |

若目录名不同，查真实位置：

```bash
find /lec/lab4 -type f -name 'RA1SHD_2048x32M8_tt_1p8_25C_syn.lib' -print
```

把 `EDA_MACRO_SOURCE` 改为该文件所在目录，再核对；不要混搭其他型号。PDK 完整性由后面的 doctor 检查。

## 4．选定本轮配置与工作目录

**服务器 Bash，部署目录：**

```bash
source "$HOME/Desktop/fullstack_chipdesign/run_env.sh"
cp server/config/design.json "$EDA_CONFIG"
if [ -r /etc/profile.d/eda.sh ]; then
    source /etc/profile.d/eda.sh
fi
python3 --version
```

需要 Python 3.8+。此前课程环境使用 3.8.10；若仍太旧，用服务器已有的 3.8+ 解释器设置 `EDA_PYTHON`。下面配置修改和入口都会使用它。

```bash
"${EDA_PYTHON:-python3}" - <<'PY'
import json
import os
from pathlib import Path
p = Path(os.environ['EDA_CONFIG'])
c = json.loads(p.read_text())
c['pdk_root'] = os.environ['EDA_PDK_SOURCE']
c['macro_source'] = os.environ['EDA_MACRO_SOURCE']
p.write_text(json.dumps(c, indent=2) + '\n')
print(p)
print(json.dumps(c, indent=2))
PY
cat server/config/io_plan.json
```

**为什么用副本：** `source.json` 记录了部署包原文件的 SHA。外部配置副本可以选择实际路径，同时保持部署文件校验有效。第一次 prepare/all 通过 `--config "$EDA_CONFIG"` 读取它。

| 配置文件或字段 | 作用；首轮建议 |
| --- | --- |
| `$EDA_CONFIG` 的 `pdk_root`、`macro_source` | 刚确认过的 PDK 和完整 SRAM 路径 |
| `system_period_ns: 20` | 系统时钟周期 20 ns，即 50 MHz；这是实现目标 |
| `cpus: 8` | 工具 CPU 数，服从服务器资源规定 |
| `target_utilization: 0.5` | 规划放置密度，给布线和修复留空间 |
| `core_size_um: null` | 按新综合面积估算核心，不套原实验尺寸 |
| `macro_xy_um: [250, 650]` | 主 SRAM 计划坐标，单位 μm |
| `max_repair_iterations: 3` | 修复尝试上限；超限保留报告并停止 |
| `hold_target_ns: 0.02` | 优化器希望争取的 Hold 余量；最终验收仍为 WNS ≥ 0 |
| `server/config/io_plan.json` | 六个信号 PAD 的边别与偏移、四边供电/POC 计划 |

第一次实现现有仓库，除库路径外保留默认参数。SDC 是规定时钟、外部接口时间和特殊路径的约束文件。IO 计划、SDC 和 Tcl 已适配当前设计；以后需要修改时，在本机改、验证、重新打包，再准备新工程。当前 profile 固定为 77 份源文件、六路信号和一个主 SRAM，不能任意换顶层后沿用。

保存位置，便于重新登录：

```bash
printf '%s\n' "$EDA_WORK" > "$CHIP_WORKSPACE/current_run.txt"
printf 'DEPLOY=%s\nWORK=%s\nCONFIG=%s\n' "$EDA_DEPLOY" "$EDA_WORK" "$EDA_CONFIG"
```

run_env.sh记录当前路径，current_run.txt供回传和GUI说明定位本轮。新一轮选用runs下的新目录，并更新这两个入口；同一轮续跑保留原路径。

| 位置 | 内容与作用 |
| --- | --- |
| Windows 仓库 | 可维护的源码、文档和 EDA 程序 |
| `$EDA_DEPLOY` | 上传的 `server/`、`rtl/` 和来源清单，用来发出命令 |
| `$EDA_WORK` | 一次实验的输入快照、报告、数据库和输出，一轮用一个新目录 |
| `/lec/pdk/tsmc180` | 公用工艺资料，工程读取并核对，不改动 |

## 6．首次实验按阶段执行

以下全在 **服务器 Bash、`$EDA_DEPLOY` 目录**。每个命令成功后再继续，不把整节一次粘贴后忽略中间错误。

### 6.1 准备工程并检查环境

```bash
bash server/bin/eda.sh prepare --work "$EDA_WORK" --config "$EDA_CONFIG"
bash server/bin/eda.sh doctor --work "$EDA_WORK"
```

**做什么、为什么：** `eda.sh` 加载环境，调用 `flow.py`。prepare 创建新工作目录，复制同源 RTL、完整 SRAM 和控制程序，生成本轮配置、绝对路径文件清单及 SHA。它拒绝覆盖已存在工作目录。doctor 提前检查 Genus、Innovus、Tcl 和实际库文件，并记录库 SHA；许可证是否可用仍需实际启动工具确认。

准备完成后，**以下相对路径都以 `$EDA_WORK/` 为根**：

```text
本轮工作目录 EDA_WORK/
├── config/                    生效的参数、SDC、库路径、IO 计划
├── src/
│   ├── chip_design/rtl/        本轮 RTL 快照
│   ├── macro/RA1SHD_2048x32M8/ 本轮授权 SRAM
│   └── filelist_syn.f          综合文件绝对路径及编译开关
├── flow/                      prepare 冻结的 EDA 控制程序
├── syn/                       Genus 脚本、报告和输出
├── pnr/                       Innovus 脚本、报告和数据库
└── evidence/                  输入身份、检查记录、实际命令、运行报告
```

| 文件 | 作用与现在要核对的内容 |
| --- | --- |
| `evidence/preparation.json` | 应记录77份RTL、正确SRAM来源和本轮工作目录 |
| `src/filelist_syn.f` | 包含 `SYNTHESIS`、`CHIP_USE_RA1SHD`，选择可综合实现和真实主 SRAM |
| `evidence/input_manifest.json` | 固定本轮输入身份，防止新代码与旧数据库混用 |
| `evidence/doctor.json` | 实际使用的库/工艺文件及 SHA，应对应已确认资料 |

```bash
cat "$EDA_WORK/evidence/preparation.json"
cat "$EDA_WORK/evidence/doctor.json"
```

prepare 后，部署入口会转到 `$EDA_WORK/flow/` 的冻结程序执行。以后更新部署文件不会悄悄改变正在运行的工程。

### 6.2 展开 RTL，先检查读入问题

```bash
bash server/bin/eda.sh elaborate --work "$EDA_WORK"
```

**做什么：** Genus 读源码和库、建立模块层次、检查语法与连接。**为什么：** 先发现缺模块、错误位宽、缺宏模型，避免完整综合后才发现输入有误。此时尚未完成工艺映射。

| 文件 | 作用及检查方法 |
| --- | --- |
| `src/filelist_syn.f` | 决定读入哪些源码 |
| `config/global_define.tcl`、`syn/scripts/syn_mmmc.tcl` | 库路径及延时/约束模型组合 |
| `evidence/genus_elaborate.log` | 控制台原文，检查读入情况和第一处 Error |
| `evidence/elaborate_check.rpt` | 设计结构检查，阅读悬空、未解析单元等异常 |
| `evidence/elaboration_status.json` | 命令完成状态，不是功能正确证明 |

```bash
less "$EDA_WORK/evidence/elaborate_check.rpt"
```

`less` 用方向键翻页、`/关键词` 搜索、`q` 退出，后面的 `.rpt`、`.md` 都可以这样读。

### 6.3 综合成具体器件，再按面积规划

```bash
bash server/bin/eda.sh synth --work "$EDA_WORK"
bash server/bin/eda.sh size --work "$EDA_WORK"
```

**做什么：** 把 RTL 映射成 TSMC180 单元和主 SRAM 连接网表，再估算核心大小。**为什么：** 物理工具需要具体器件及连接；新 NPU/DMA 的面积不能沿用原实验尺寸。

| 文件 | 作用与检查重点 |
| --- | --- |
| `config/constraints_my_soc_top.sdc`、`config/user_define.tcl` | 本轮时钟及时间要求，系统周期应为 20 ns |
| `syn/scripts/genus_synthesis.tcl` | 组织优化、工艺映射、报告和导出 |
| `syn/my_soc_top/my_soc_top_postsyn.v` | 工艺映射后的网表，是 Innovus 输入 |
| `syn/my_soc_top/reports/runtime/check_*.rpt` | 综合各阶段结构检查 |
| `syn/my_soc_top/reports/area/area.rpt` | 单元数、面积、CPU/NPU/DMA 层次，确认未意外裁掉逻辑 |
| `syn/my_soc_top/reports/timing/` | 综合关键路径，互连仍为估计 |
| `evidence/synthesis.json` | 映射和面积摘要，应有一个真实主 SRAM，无非预期数据锁存器面积 |
| `evidence/floorplan_plan.json` | 核心大小、密度和宏留白预留；只是规划结果 |

```bash
cat "$EDA_WORK/evidence/synthesis.json"
cat "$EDA_WORK/evidence/floorplan_plan.json"
less "$EDA_WORK/syn/my_soc_top/reports/area/area.rpt"
```

[报告分析](报告查找与分析.md)解释如何读面积、关键路径、门控和功耗。单元面积不是裸片面积；最终还要留宏、外围、供电和布线空间。

### 6.4 后端 01–14：外形、外围和主 SRAM

```bash
bash server/bin/eda.sh pnr --work "$EDA_WORK" --until 14
```

**做什么：** 导入综合网表，建立核心/裸片边界，放角块、信号/供电 PAD、键合焊盘、外围填充及主 SRAM，连接接口并建立物理端口。PAD 是芯片边缘实际输入输出或供电单元。**为什么：** 先固定外围和宏，后续才知道普通逻辑能放在哪里。

| 文件 | 作用与完成效果 |
| --- | --- |
| `config/io_plan.json` | 六信号 PAD 的边别和偏移、四边各七个供电/上电控制单元 |
| `evidence/geometry.json` | 工具网格吸附后的真实边界及派生端口坐标 |
| `evidence/08_topology.json`、`11_pg_topology.json` | 原信号端点保留与四种供电网络归属核对 |
| `pnr/generated/` | 根据本轮几何及宏实例生成的 Tcl |
| `evidence/commands/01/` 至 `14/` | 实际执行过的 Tcl 正文 |
| `evidence/step_14.json` | 六信号和四电源物理端口的矩形、方向、用途核对 |

六路信号是 `clk_i`、`rst_ni`、`tck_i`、`tms_i`、`td_i`、`td_o`。第 04 步只保存插 PAD 前的 prePad 恢复点；第 07 步才放六个信号 PAD，时钟/复位在北边，四路 JTAG 在南边；第 08 步接线。第 09 步放 28 个供电/POC 单元，不移动六个信号 PAD。POC 是上电控制单元。第 10 步为这 34 个边缘单元加封装金线接触的键合焊盘。

每个通过步骤保存 `step_NN.json` 和 `stepNN.enc`/配套数据库。检查点是工具的恢复点；`.enc` 加载脚本与 `.enc.dat` 数据库要成套保留。

### 6.5 后端 15–23：真实供电路径及辅助单元

```bash
bash server/bin/eda.sh pnr --work "$EDA_WORK" --until 23
```

**做什么：** 建电源环、条带、单元行电源轨，连接供电 PAD，再插阱连接和去耦单元。**为什么：** 网表中的 VDD/VSS 只代表网络归属，还要有金属把电送到器件。阱连接为器件所在硅体区域提供参考电压，去耦电容缓和短时供电变化。

| 文件 | 作用与检查重点 |
| --- | --- |
| `pnr/my_soc_top/my_soc_top_pg_drc.rpt` | 供电金属的宽度/间距等几何检查 |
| `pnr/my_soc_top/my_soc_top_pg_noDangling.rpt` | 排除悬线检查的中途供电报告，不是最终完整供电验收 |
| `evidence/step_22.json`、`native_io_rails_check.json` | IO 供电抽象限制及原生几何证据 |
| `pnr/my_soc_top/my_soc_top_welltap.rpt` | 阱连接覆盖检查 |
| `pnr/my_soc_top/my_soc_top_postPhysCells_pg_drc.rpt` | 加辅助单元后的供电几何复核 |

`VDD/VSS` 是核心电源/地，`VDDPST/VSSPST` 是 IO 电源/地，四网分开。第 22 步仅对有证据支持的两项 IO 库抽象限制分类，不能忽略任意 no routing。

### 6.6 后端 24–26：普通逻辑放置和布线前诊断

```bash
bash server/bin/eda.sh pnr --work "$EDA_WORK" --until 26
```

**做什么：** 把 CPU/NPU/DMA 的标准单元放到合法行，插提供稳定逻辑常量的 Tie 单元，检查位置和时序。**为什么：** 位置决定互连长度，控制脚的常量也需符合工艺。

| 文件 | 作用与检查重点 |
| --- | --- |
| `pnr/my_soc_top/my_soc_top_place_check.rpt` | 放置合法性、未放置单元 |
| `pnr/my_soc_top/my_soc_top_postTie_place.rpt` | Tie 插入后的复核 |
| `pnr/my_soc_top/reports/preCTS/`、`evidence/step_26.json` | 建时钟树前的时间/电气诊断，不是最终验收 |

### 6.7 后端 27–29：建立时钟分配树

```bash
bash server/bin/eda.sh pnr --work "$EDA_WORK" --until 29
```

**做什么：** 插时钟缓冲，把时钟送到各寄存器，再检查和阶段性修复 Hold。CTS 就是建立时钟树。**为什么：** 寄存器位置不同，时钟到达时间也不同，需要控制差异。

| 文件 | 作用与检查重点 |
| --- | --- |
| `pnr/my_soc_top/reports/postCTS/` | 时钟树建立后的时间分析 |
| `pnr/my_soc_top/reports/postCTS_holdFix_check/` | 阶段性 Hold 修复后的独立复核 |
| `evidence/step_28.json`、`step_29.json` | 两阶段结果，允许记录留到布线后处理的残项 |

Setup 检查数据是否及时到达下一次采样，Hold 检查数据是否保持足够久、没有过早改变。最后两者都要通过。

### 6.8 后端 30–34：布线、修复、最终检查和导出

```bash
bash server/bin/eda.sh pnr --work "$EDA_WORK" --until 34
```

**做什么：** 给网络分配真实金属线和过孔，修复天线效应，提取电阻电容，修复时序/电气违规，插核心填充，再检查和导出。**为什么：** 真实布线会改变延时和负载，最终状态需重新验收。制造阶段金属积累电荷可能损伤器件，这就是要检查的天线效应。

| 文件 | 作用与完成标志 |
| --- | --- |
| `flow/tcl/fanout.tcl`、`evidence/fanout_plans/` | 第 32 步按当前报告给扇出超限网加缓冲分支，不复用历史网名 |
| `pnr/my_soc_top/reports/postRoute_holdAuto_check/` | 第 32 步真实 RC 下修复后的独立时间分析 |
| `pnr/my_soc_top/reports/postFiller/` | 最终填充后的时间和电气报告，用它判断最终时间结果 |
| `evidence/step_33.json` | 最终放置、时序、电气、DRC、天线、核心供电和信号连接核对 |
| `evidence/step_34.json`、`export_audit.json` | 端口、实例路径、寄生和 GDS 引用关系核对 |
| `pnr/my_soc_top/outputs/manual_final/` | 最终 DEF、网表、SDC、SDF、SPEF、LEF、GDS |

RC 指导线电阻和电容。DRV 指负载电容、信号变化时间、扇出等电气限制；扇出指一个驱动要带多少负载。该 SoC 曾因布线新增天线二极管而扇出超限，脚本会按当前报告插缓冲、重新布线/分析，不提高限制或放宽时钟。

**完成标志：** 命令成功，status 显示 34，第 33/34 步检查齐全且没有未解决工具错误；不能只看 GDS 出现了没有。

```bash
bash server/bin/eda.sh status --work "$EDA_WORK"
cat "$EDA_WORK/evidence/step_33.json"
cat "$EDA_WORK/evidence/step_34.json"
```

`--until N` 表示从最后通过点连续执行到 N。到 14 后用 `--until 23` 执行 15–23；已完成目标拒绝重复执行。想逐步观察，就依次 `--until 1`、`2`……`34`，边读[34 步附录](讲义34步与文件对照.md)。

按五项分析，详细命令和字段解释见[报告查找与分析](报告查找与分析.md)：

1. **来源与范围：** `source.json`、`preparation.json`、`last_step.txt` 和工具错误记录说明哪份源码、哪轮运行、是否完成。历史结果的分段来源见结果说明；本指南从当前RTL开始执行，不导入其他工程的开发检查点。

## 9．失败、断线后怎样查原因和继续

按第 5 节恢复路径，先检查状态。正在运行时，可在另一 SSH 终端只读查看日志，不同时启动会加锁的 report/package。

```bash
bash server/bin/eda.sh status --work "$EDA_WORK"
ls -lt "$EDA_WORK/evidence/"*.log
```

综合原文如下；后端日志取上面实际列出的 `innovus_起步_to_终步.log`，名称随分段变化：

```bash
tail -n 80 "$EDA_WORK/evidence/genus_synthesis.log"
```

用 less 找第一处 `EDA_STAGE_FAILED`、`EDA STOP`、实际 Error，再向前读上下文；最后一行经常只是前面失败的结果。

| 情况 | 处理方法 |
| --- | --- |
| 缺库、宏路径错误 | 修配置副本，换新工作目录 prepare |
| RTL/SDC/IO/控制程序需改 | 本机修改、验证、重新打包，新部署、新工程 |
| 中断但输入未变、没有未解决工具错误 | 确认旧进程退出，再 all 或更大 until 从通过点恢复 |
| 已有未通过验收的综合输出 | 保留诊断，准备新工程；不覆盖混用残留综合输出 |
| `unexpected_tool_errors.json` 存在 | 读原始错误；入口拒绝旧工程继续，修原因后新建工程 |
| 时序/DRC/连接未清零 | 读对应报告；修复次数有上限，失败不放宽目标 |
| 遇到 `flow.lock` | 先查锁内 PID 和工具子进程，不直接删锁或批量杀进程 |

只有确认锁记录中的本机 Python 和工具子进程均退出，才可运行：

```bash
bash server/bin/eda.sh unlock --work "$EDA_WORK"
```

unlock 会核对进程，不能用它停止任务。恢复加载上一个通过的完整检查点；不要修改 `input_manifest.json`、`step_XX.json`、`last_step.txt` 强行跳过。
