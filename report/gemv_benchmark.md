# RAW GEMV 与纯 CPU 周期对照

2026-11-18 首次完整 SoC RTL 实测中，动态打包版 CPU＋RAW 在五个场景下都比纯 CPU 慢。32×64 满块为 0.797×，33×65 尾块为 0.250×；主要耗时是 CPU 在运行时重排权重，尚未体现端到端加速。之后已完成固定权重的软件优化，新的结果和使用入口见 [优化报告](gemv_optimization.md)。

完整计数、源码 SHA、固件和日志 SHA 见 [测量记录](gemv_benchmark.json)。这里的结论针对当前单向量运行时和下面的 RV32IM 基线。

## 比较结果

加速比定义为 `纯 CPU 周期 / CPU＋RAW 周期`，大于 1 才表示 RAW 更快。每个后端独立冷复位，使用相同的 CV32E40P、AXI、DMA、NPU、128 B 指令缓存和 8 KiB SRAM RTL。功能仿真时钟为 10 ns，不据此声称实际芯片达到 100 MHz。

| 场景 | 有效乘加数 | RAW 块数 | 纯 CPU 周期 | CPU＋RAW 周期 | 加速比 | RAW 用时 / CPU 用时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 32×64 满块 | 2048 | 1 | 45624 | 57242 | 0.7970× | 1.255× |
| 33×65 尾块 | 2145 | 4 | 47397 | 189720 | 0.2498× | 4.003× |
| 1×129，归约超 INT22 | 129 | 3 | 2832 | 133116 | 0.0213× | 47.004× |
| 17→9→5→3 三层网络 | 213 | 3 | 6074 | 134036 | 0.0453× | 22.067× |
| 65→3→1，64 位重定标 | 198 | 3 | 4626 | 133037 | 0.0348× | 28.759× |

纯 CPU 使用手写四项展开的标量 RV32IM 循环：两个有符号 `LB`、`MUL`、`ADD` 计算一项，剩余 1～3 项使用尾循环。bias 只加一次，累加为 INT32，层间 ReLU、64 位乘积、舍入、移位和饱和代码与 RAW 路径共享。两条路径使用相同紧凑行优先权重和模型数据，CPU 不执行填充行和列，也不访问 NPU。

## 计时与正确性

CPU 在 `0x80001fc0` 写 BEGIN=1 和 END=2。该地址位于 2048 B W1 工作区之后、成功状态字之前，不占用模型数据，也不新增 RTL 寄存器。testbench 以这两次写入在实际 SRAM 接口被接受的时钟边沿之差计时。

BEGIN 位于指针配置和后端初始化之前；END 位于全部层输出写回之后，RAW 路径还包含恢复 `MODE=0` 的开销。区间包含 CPU 初始化、每块输入打包/补零、每块 2048 B 权重打包、START、DMA、完成轮询、RAW 索引/READY/DATA 访问、INT32 归约和层间处理。两条路径都保留相同的 BEGIN/END 标记序列，结束标记指令的固定开销计入结果。

全部 CPU golden 自检在 END 之后执行。被动 testbench 同时逐字节核对所有层的输出写入，要求每个结果在 END 之前已产生，禁止计时区间内从 SRAM 读取 golden；纯 CPU 发生 NPU 请求、DMA 自动启动或 NPU busy 时立即失败。这些被动核对不会占用模拟 SoC 的执行周期。源码、相同的数据区和每份固件均以 SHA 绑定。

阶段划分使用生成固件中各阶段入口的合法 ID 发射 PC，观察实际执行的循环入口，阶段切换不插入指令。各阶段是互不重叠的时钟窗口，总和等于 BEGIN→END 周期；边界附近的取指、流水和总线等待归入相邻窗口，不作为逐条指令退休归因。另以真正的 NPU START/DONE 边界累计每个 RAW 块的硬件计数，并逐块检查时间差与 `cycle_count` 相等、`fc1_cycles=128`、`fc2_cycles=0`。

新结果与早期 `run_generic_soc.py` 的 188031 等周期不是同一计时口径：早期结果包含逐层 CPU 自检；本次将自检移到 END 之后，加入了显式计时标记，代码地址与指令缓存行为也随之变化。

## 时间花在哪里

32×64 满块的 RAW 路径如下：

| 阶段 | 周期 |
| --- | ---: |
| 初始化、描述符与 bias 准备 | 748 |
| 输入打包与 MMIO 写入 | 1041 |
| CPU 权重打包 | 51684 |
| 启动、NPU/DMA 执行及完成轮询 | 732 |
| RAW 读回、INT32 归约及块间控制 | 1300 |
| 输出处理、模式恢复及 END | 1737 |
| 总计 | 57242 |

NPU 从 START 到 DONE 为 715 拍，属于上表 732 拍窗口；其中乘加发射为 128 拍，DMA/MAC 总 overlap 为 124 拍。不能将这些内部计数再次加到总时间中。

五个场景的权重打包占比为 90.29%、93.69%、95.64%、94.24%、95.31%。满块仅打包权重就用了 51684 拍，已超过纯 CPU 完成整个任务的 45624 拍。原因是当前通用代码逐字节做边界判断、地址乘法、读取、移位与拼接，每个 RAW 块都写满 2048 B；NPU 中快速完成的乘加没有抵消这部分 CPU 工作。

尾块进一步降低有效乘加占比。33×65 的四块中仅有 `2145/8192≈26.18%` 为有效计算；1×129 的三块仅有 `129/6144≈2.10%`。因此该版本适合作为功能正确的通用执行路径，当前五个单向量场景应优先选择纯 CPU 以减少时延。

若继续追求 RAW 加速，优先在软件/编译层预排固定权重、减少内层地址计算与边界判断、复用打包结果，并根据块大小选择 CPU 或 RAW。8 KiB SRAM 的容量约束仍须满足。优化后需按相同边界重测；本轮没有实现这些优化，也没有通过扣除打包周期来推算实际加速比。

## 复现与回归

```powershell
.\.venv\Scripts\python.exe test/int8/run_gemv_benchmark.py `
  --vsim D:\modeltech64_2019.2\win64\vsim.exe
```

可用 `--case full_32x64` 等限制场景，`--out` 指定尚不存在的输出目录。默认执行五组模型、两个后端，共十次真实 SoC 仿真。每个目录保存模型、固件、布局、参考数据、阶段 PC 和完整 `soc.log`。本轮本地证据目录为 `test/int8/runs/gemv_bench_20261118_141746/`；该目录被 Git 忽略，持久结果为上述 JSON。

- 十次 CPU/RAW SoC 仿真全部通过，260 项规划/整数参考检查通过。
- 补充纯 CPU 五层程序覆盖 K=2/3/4/7/8、INT8 符号极值、MULT=0、SHIFT=0、ReLU 和饱和；主对照场景另外覆盖 K 余 1 及 64 位舍入进位。
- 原有四个默认 RAW 固件的 8 KiB 镜像 SHA 与修改前逐个相同，未启用 benchmark 的现有入口行为保持一致。
- 原有 41 组计算、8 组 DMA 响应及 Boot 周期检查通过；75 个硬件源码 SHA 检查通过。RTL 和原 HAR testbench 无修改。

实现入口为 [run_gemv_benchmark.py](../test/int8/run_gemv_benchmark.py)，完整 SoC 的计时、正确性及隔离检查位于 [tb_gemv_benchmark.sv](../test/int8/tb_gemv_benchmark.sv)；[generic_firmware.py](../test/int8/generic_firmware.py) 增加可选 CPU 后端和 benchmark 生成方式，默认仍生成原有 RAW 固件。
